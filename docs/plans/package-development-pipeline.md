# Configurable package development and reuse pipeline — review proposal

Status: proposed implementation plan, reviewed 2026-09-13 against commit
`8ceaecb26ae4a2666459ad843f77deff8b4fd748`. Existing hook work was present during
the read-only audit. A fresh development MCP probe passed 35 checks. The two
bounded reproductions below ran in private temporary fixtures; their logs and

## Intended behavior

Build the reusable orchestration inside Praetor. Treat organization, forge, module namespace, catalogs, package destination, release channels, workstation roots and policy bindings as explicit deployment inputs. `golusoris` is the owner-selected deployment example; the public app must work identically with synthetic `example` identities. Default to read-only inventory and candidate plans until a stage is admitted. No blocking user question is needed to begin the stages below.

The missing piece is a source-bound link from evidence to reviewed capability demand, implementation, consumer verification and promotion. Existing modules provide many ingredients, but neither the accepted ADR text nor a green Praetor unit suite establishes a working global development loop.

## Minimal shared boundaries

Use one orchestration/application service with explicit injected interfaces, consistent with ADR0009. Do not create a framework or service locator for every noun. Keep source scanning, provider transport, runtime execution and CLI/MCP/IDE formatting in existing adapters.

- **Package policy and catalog**: extend internal/config with typed operational fields for target forge/org/module namespace, package kind (library/framework/module/template), capability namespace, selected catalog, dependency constraints, lifecycle/stage enablement and runtime adapters. Governance combines by tightening; operational destination follows documented precedence. One immutable resolved object and digest goes to demand, generation, dogfood and release consumers. No inferred home-directory configuration.
- **Evidence and relations**: one versioned manifest relates Source -> Claim/Requirement -> ReuseDecision -> PackageTask -> Change -> Verification -> ReleaseCandidate. Store stable IDs, parent IDs, source commit/content hashes, command/toolchain identities, actual outputs, captured time, coverage, and trust class. Reuse notebook/harvester hashes and existing journal/receipt mechanisms; projection adapters produce Markdown, issues and memory pages. Do not merge their unequal meanings into one generic success boolean.
- **Stage executor**: pure transition planner plus explicit execution admission. Each transition has prerequisites, scope, expected source, budget, implementation availability and repeat/idempotency key. Reuse repairrun attempts and bounded command wrappers. Typed states: observed, candidate, blocked, ready, running, failed, scoped_verified, consumer_verified, release_ready, published; publication needs remote readback.
- **Adapter capability manifest**: each language/forge/client declares what it can actually detect, plan, execute, verify and publish. Absence is unsupported. Go-first implementation is compatible with polyglot architecture; it is not universal completion. Keep language-specific import/API compatibility proof inside adapters.

## Hardcoded bindings and public/private boundary

Concrete source migrations: `needs/requests.go:65,76`; `needs/harvester.go:165-191`; `needs/framework.go:16`; language analyzers and `catalog.go` replacement imports; `cmd/standardsctl/issue.go:56-57`. Generic `GolusorisReplacement` wire field needs additive replacementTarget with a documented compatibility migration rather than a silent rename. The proposed generic policy would supersede ADR-0007's hardcoded deployment designation through a new ADR; ADR0009's separation of archetypes and release flavors remains valid.

Targeted source search found no `/home/` or `/Users/` literal in production internal/cmd Go, archetype YAML or template files. Absolute home paths seen in local evidence are resolved runtime/workstation bindings, not proof a production literal exists. Public docs should use `<workspace-root>`, `<catalog-root>`, `<state-root>`, `<owner-config>` and logical source IDs. Private config binds them to actual directories; diagnostics may show a confined path but exported/public artifacts must redact it while retaining content hashes. Never copy personal config into public templates.

## Prior knowledge and limits

No dependency/framework shopping is needed to start. Use existing Go module, config, bounded I/O, native Git and adapters. Prior package research remains candidate research, not adopted runtime capability. A shared library extraction follows demonstrated second-consumer reuse, compatibility and publication evidence. This plan makes no claim of full pipeline completion or savings before those measurements.
