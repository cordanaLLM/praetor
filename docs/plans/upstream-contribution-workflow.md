# Upstream contributions within the shared package pipeline

Status: proposed implementation, reviewed 2026-09-13 against Praetor commit `76832ee75c8964f2ffeac338a6a3aa9473c23eda`. The development MCP probe passed 35 checks with source digest `6aedd54101efe1fbc1e5951dcde413c00a63aac3953cef301ce7286356966d4f`. The checkout also contained unrelated work; inspected source hashes and bounded local reproductions were retained privately. This audit did not contact an upstream forge, execute a model, publish anything, or establish end-to-end contribution readiness.

Extend the [package development pipeline](package-development-pipeline.md), whose reuse decisions already include upstream contribution. Use its common policy, evidence relations, stage planner, executor admission and adapter capabilities. A contribution is a path through that pipeline, not another issue database, framework, bot, or per-IDE implementation.

## One contribution record in the shared evidence graph

Relate the existing `Finding/ReuseDecision -> PackageTask -> Change -> Verification` objects to one contribution record. Retain separate evidence for upstream identity, publication and downstream maintenance:

`finding -> upstream reproduction -> candidate patch -> local reviewed draft -> authorized publication -> upstream acceptance -> released fix -> downstream verification without patch -> patch retirement`

The record needs stable IDs and references, not duplicated artifact bodies:

- Finding ID, originating consumer/replay IDs, classification, affected package coordinate/version and exact source commit. Distinguish Praetor integration defects, upstream application defects, environment/toolchain failures and unsupported coverage.
- Canonical upstream forge/host/repository identity; exact reproduction base; optional fork identity and proposed head/base. A Git remote name, module-name heuristic or ambient `GITHUB_REPOSITORY` must not choose the publication target.
- Search observations with query scope, timestamps, pagination/completeness, matching issue/PR IDs, head/merge commits and uncertainty. Candidate matches are reviewed before linking; similar titles alone do not merge findings.
- Reproducer, toolchain/command identity, expected failing assertion, before/after source and artifact hashes, actual result counts, omitted gates and coverage. Observed failure is distinct from a source-verified regression.
- Patch artifact, allowed paths, original license/attribution references, local draft body, review decision, and evidence bundle digest. Exported text is a separately reviewed sanitized projection.
- Publication authorization bound to the exact target, operation, patch/head and rendered body digest; durable attempt/idempotency identity; remote issue/PR IDs and readback. Token presence, ownership, a policy setting or an agent's choice cannot substitute for explicit external-publication authorization.
- Upstream merge/release observations and each downstream consumer's patch/bump state. Model upstream resolution (`open`, `duplicate`, `declined`, `accepted`, `released`, `reverted`, `unknown`) separately from local preparation/execution state. A failed or declined contribution remains useful evidence.

Deduplicate one compatible upstream cause across consumers while retaining each affected version and reproducer. Different causes, incompatible versions or licensing/runtime constraints must remain separate. A changed source pin, patch, target, or required toolchain invalidates dependent verification and publication admission. A content digest proves integrity relative to captured bytes; source authenticity requires its own verified binding.

## Configurable policy, with one resolver and explicit capabilities

Extend the package policy's existing owner/org/forge/repository/stage inputs rather than introducing a new config store. Resolve once, preserve source provenance and pass the same immutable digest to planning, execution, CLI, MCP and future IDE/bot adapters.

| Setting group | Required behavior |
|---|---|
| Identity | Explicit upstream target, optional contributor fork/destination, package coordinate and policy owner. Public examples use `example/upstream` and `example-contributor/upstream`; operational settings supply actual bindings. Credentials remain private references. |
| Stage admission | Independently enable read-only discovery, local reproduction, local patch preparation, publication, follow-up and downstream retirement. Governance constraints only tighten; operational destination precedence is documented. Missing explicitly selected config errors; unknown capability blocks its stage. |
| Native execution | Exact source/toolchain pins, admitted commands, filesystem/network scope, time/output/attempt/cost limits, applicable hook adapter and coverage requirements. Keep upstream execution separate from public governance scanning. Use the shared executor and current router admission work; do not add a parallel dispatcher. |
| Contribution requirements | Pinned upstream contributing/license/notice/template references, attribution and DCO/CLA requirements, reviewer policy and report visibility. Check actual declared requirements; do not forge signatures or attest a CLA on another person's behalf. |
| Publication | Allowed operation and target policy, remote draft requirement where selected, sanitized export rules, authorization/readback and retry limits. Publish remains unavailable when a driver cannot satisfy the requested contract. |
| Maintenance | Recheck cadence/budget, expected release channel, downstream consumer bindings and patch retirement conditions. No blanket fleet schedule is activated by adding a contribution record. |

Prefer small additive capability interfaces backed by the existing `internal/forge` transport for contribution search/status and draft publication, rather than making every driver fake all methods. Declare which operations each adapter implements. The application service uses these interfaces and the existing bounded storage/execution primitives; adapters format results only. Preserve existing public signatures and add explicit versioned fields. Corrections to misleading certification or previously accepted incomplete evidence need a documented migration requiring fresh evidence.

## Stage contract

1. **Discover and classify.** Import retained finding evidence and inspect the selected upstream's current contribution rules. Search both open and closed issues and PRs and relevant merge/release history. Bound requests/results; exhaustion, authentication failure, rate limits or stale results mean partial/unknown, never “no duplicate exists.” Refresh relevant matches before publication. Read-only discovery may stop at a linked existing report, upstream fix, invalid finding or unsupported environment.
2. **Reproduce on exact upstream source.** Preserve a clean immutable base and run the upstream's actual documented commands in a disposable admitted environment. Record native failing tests, prerequisites and failure controls; do not replace upstream tests with a Praetor audit. A new reproducer must fail on the unchanged base and avoid the observed failure mechanism on the candidate. Environment failures do not establish an upstream defect. Unavailable native execution leaves a report candidate with an explicit limitation.
3. **Prepare a minimal local change.** Reuse the bounded repair/command infrastructure where its current contract fits. Extend through reviewed language adapters when it does not; do not loosen the narrow repair API silently. Keep the patch minimal and avoid unrelated governance adoption. Verify exact-base application, regression tests, relevant upstream gates and source cleanliness. Keep original-corpus/consumer replay separate from scoped patch verification. Reuse a reviewed upstream fix when it already exists and record its attribution.
4. **Build the reviewable draft.** Produce a local bundle with problem, minimal reproduction, expected/actual behavior, affected source/version, search matches, patch, verification and omitted gates, attribution, target and rendered issue/PR text. Report-only contributions can omit a fix but cannot claim fix verification. Keep raw transcripts, private settings, cluster guides, workstation paths and credentials out of exports. An LLM may draft text; deterministic validation and review establish the admitted artifact. Local draft creation does not create a remote draft PR.
5. **Publish only the authorized artifact.** Present the concrete bundle for explicit approval of external mutation. Recheck target/head/digest and duplicate status immediately before execution. Read back the exact issue/PR identity, draft state and head. Branch/fork creation and push are separate external operations and must be included in the authorization scope. Preserve normal hooks. Persist attempted/confirmed/ambiguous outcomes; after timeout or crash, inspect remote state before retrying so one accepted create cannot become two submissions. Creating an issue and PR is not an atomic transaction; retain partial success. No merge or unsolicited comment is implied.
6. **Observe acceptance and maintain downstream.** Read current upstream review/merge status and propose requested changes through the same candidate/review path. Do not equate closed with merged or merged with released. Bind accepted fix to its actual merge/squash/cherry-pick result and released artifact/version, accounting for backports or reverts. A downstream bump is prepared and tested in isolation without the local patch. Remove only the exact unchanged retained patch after that consumer passes the required checks; protect changed files with snapshot comparison and keep rollback/provenance. Partial fleet success retires patches per consumer, not globally.

A unit test suite or catalog declaration alone does not establish a working upstreaming loop.
